# Changelog

Change notes live in two places, and they do different jobs. `.changeset/*.md` holds the **raw record written the day the change was made**; the `CHANGELOG.md` inside each package is the **release-time summary generated by changesets**. This page has a narrower scope: where the versioning stands right now, and what the next release will carry.

## How releases work

Versions move with the changes, not with whoever remembers to write them down afterwards. Four steps; the scripts live in the root `package.json`:

| Command | What it does | What you still have to do |
| --- | --- | --- |
| `pnpm changeset` | Interactively picks the affected packages and bump level and writes one `.changeset/xxx.md` | Commit it together with the code it describes |
| `pnpm version` | Runs `changeset version`: consumes every changeset, raises package versions, writes each package's `CHANGELOG.md`, deletes the changesets it consumed; then `pnpm install --no-frozen-lockfile` so the lockfile catches up | **Commit it yourself** (`chore(release): x.y.z`) |
| `pnpm exec changeset tag` | Tags every package at its current version as `<pkg>@<version>` | `git push --follow-tags` — a plain `git push` does not push tags |
| `pnpm release` | `pnpm build` first (with `NODE_OPTIONS=--max-old-space-size=8192`), then `changeset publish` | Every package is `private`, so publishing is currently a no-op; kept for the day a package does go to npm |

Fields in `.changeset/config.json` that change the behaviour:

- `"fixed": [["@antdv/*", "@antdv/*"]]` — moves every workspace package **in lockstep** to the same version. The cost: one patch on one package nudges the whole set by one. The gain: version skew between packages cannot pile up. **It is a mechanism that fires at release time, not a live invariant** — it aligns the set once per `version` run. How the landing number is computed is covered in "How the lockstep number is computed" below.
- `"privatePackages": { "version": true, "tag": true }` — all `@antdv/*` packages are `"private": true` (nothing is published to npm), and this setting decides whether private packages take part in versioning and tagging at all. It is spelled out rather than inherited: changesets changed this default late in 2.x, and a release chain should not rest on somebody else's default. With it on, non-published members such as `@antdv/web` and `@antdv/backend-mock` still get versions and tags, so a deployed build can be matched to a number.
- `"changelog": "@changesets/changelog-git"` — generated entries carry the short commit SHA and need no credentials. This used to be `["@changesets/changelog-github", { repo: "junjie73-blip/antdv-next-admin" }]`, which looks every changeset's commit up on the GitHub API to find its PR number — and **without `GITHUB_TOKEN` it aborts the whole `version` run** (`Please create a GitHub personal access token…`), reporting afterwards that no files were touched, i.e. the release simply cannot finish. No package ships to npm, so PR links are not a requirement here, and the provider was switched to `changelog-git`. To go back: change the config, the root devDependency and its catalog entry together, and provide `GITHUB_TOKEN` locally and in CI.
- `"commit": false` — `version` touches files but does not commit, so you write the message (the convention so far is `chore(release): x.y.z`, which is what `v0.0.3` carries).
- `"baseBranch": "main"` — the branch changesets measures "what belongs to this round" against.

### How the lockstep number is computed

The landing version of a `fixed` group = the **highest version currently in the group** plus the largest bump level of the round. It is not "start from 0.1.0". Before this release the 34 members sat on five different numbers (`0.0.0` / `0.1.0` / `0.4.0` / `0.5.0` / `5.8.0`): `layouts` had been hand-written as `0.5.0` at extraction time, and `scripts/turbo-run` / `scripts/vsh` still carried `5.8.0` inherited from upstream `vue-vben-admin`. Run once as-is, and the whole set — including `docs` and the five lint-config packages, still at `0.0.0` — would have landed on `5.9.0`, inventing five phantom prior releases.

The fix applied here: **set every member to `0.0.0` first, then run `version`**, so the landing point is 0.1.0. The 34 local tags produced by an earlier `changeset tag` — never pushed, and never matching a `version` result — were deleted (the remote had 0 tags), so `HEAD` does not carry two generations of tags at once.

::: warning Two rules that still hold

- New packages are born at `0.0.0`. The highest number in the lockstep group decides where the whole set lands, so hand-writing a "more official-looking" number quietly moves the baseline for everything.
- When a package is renamed or split, the package names registered in `.changeset/*.md` are part of the rename too (next section).

:::

## A renamed package breaks the whole release chain

`assemble-release-plan` hard-fails the chain when a changeset names a package that is not in the workspace — it does not skip that changeset. `status`, `version` and `publish` all throw at the same step, so no release completes until it is fixed. This is exactly what blocked 0.1.0:

```
Error: Found changeset monorepo-shared-packages for package @antdv/composables
which is not in the workspace
```

`.changeset/monorepo-shared-packages.md` had been filed with pre-rename names: `@antdv/composables` became `@antdv/hooks` when `packages/composables` moved to `packages/core/hooks`, and the common components once called `@antdv/ui` now live in `packages/core/ui-kit/common-ui` (`@antdv/common-ui`) — the other half of that same split became `@antdv/icons`. Both bump declarations were rewritten to the current names.

::: tip Why nobody caught it earlier

No CI job touches changesets (`.github/workflows/` contains only `docs.yml`), so this only surfaces on the day someone actually tries to release. `pnpm changeset status` is read-only and safe to run as often as you like — add it to the pipeline if you want the break caught before release day.

:::

## Maintaining this page

After a release, move the whole "Pending changes" block into a new row of the version table and re-list whatever is left in `.changeset/`. Never write the entry count from memory — count it:

```bash
ls .changeset/*.md | wc -l
```

Same for the version distribution:

```bash
for f in $(find apps packages internal docs scripts -name package.json \
  -not -path '*/node_modules/*' -not -path '*/dist/*' -not -path '*/.output/*'); do
  node -e "const p=require('./$f');if(p.name)console.log(p.version, p.name)"
done | sort
```

Tags: `git tag -l '@antdv/*'`. This page is a hand-maintained summary; **each package's `CHANGELOG.md` and `.changeset/` are the sources of truth**. When they disagree with this page, they win — and fix the page.
