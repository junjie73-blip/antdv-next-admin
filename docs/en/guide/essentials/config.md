# Configuration

There are **three unrelated configuration surfaces** in this repository, and confusing them causes most of the debugging pain:

| Surface | Lives in | When it takes effect | Restart needed |
| --- | --- | --- | --- |
| Build-time env vars (`VITE_*`) | `apps/web/.env*` | read in Node (plugins, dev server) _and_ in the browser (`import.meta.env`) | yes, restart the dev server |
| User preferences | `packages/core/preferences` + `apps/web/src/settings/index.ts` | at runtime, persisted to localStorage | no, a reload is enough |
| Application constants | `apps/web/src/config/*.ts` | compile-time constants | no (HMR) |

The first decides how the bundle is produced and which backend it talks to, the second decides what the UI looks like, the third holds hard-coded product decisions (the route allow-list, the home / login paths, the scrollbar flavour). Preferences are **not a runtime copy of a config file**: they have defaults, sanitization, and migration — see below.

## Env vars: two read paths, opposite types

Vite merges `.env` → `.env.[mode]` → `.env.local` → `.env.[mode].local` (later wins; `.local` files are not committed). What is committed today:

- `apps/web/.env`: `VITE_NAMESPACE`, `VITE_APP_TITLE`, `VITE_MOCK=false`, `VITE_MICRO_APP=false`, `VITE_WS_URL=`
- `apps/web/.env.development`: `VITE_PORT=6080`, `VITE_INJECT_APP_LOADING`, `VITE_DEVTOOLS`, `VITE_MOCK=true`, `VITE_APP_BASE_API=/api`, `VITE_MOCK_SERVER=http://localhost:5320`
- `apps/web/.env.production`: `VITE_ARCHIVER`, `VITE_COMPRESS=gzip`, `VITE_PWA`, `VITE_VISUALIZER`, `VITE_PORT= 9080`, `VITE_CACHE_ENCRYPT_KEY`

The typing works in opposite directions on the two sides, which is exactly how bugs get in:

- Node side: `loadEnv()` in `internal/vite-config/src/utils/env.ts` pipes the result through `parseLoadedEnv` from `vite-plugin-env-parse`, so a `true` in `.env` arrives as a real boolean and `6080` as a number. Writing `envConfig.VITE_X === 'true'` is always false.
- Browser side: `import.meta.env.VITE_X` is **always a string** (`'true'`, `'false'`, `''`). Writing `=== true` is always false there too, for the opposite reason.

Hence two `isEnvEnabled` implementations: the Node one in `internal/vite-config/src/utils/env.ts` (it also accepts the number `1`, which `parseLoadedEnv` produces) and the browser one in `packages/core/base/shared/src/utils/env.ts`, imported as `@antdv/shared/utils/env`. Both accept only `true / 1 / on / yes`, ignoring case and surrounding whitespace; everything else, including `''` and `'0'`, is false. `types/env.d.ts` is generated by `envParse`, and the `boolean` annotations in it describe the _literal in the file_, not the runtime type — the warning sits in that file's header.

::: warning

Three variables that look live but are not read anywhere

- `VITE_NAMESPACE`: appears only in `.env` and `types/env.d.ts`, zero references in code. The cache prefix actually comes from `VITE_APP_TITLE`, so don't trust the name.
- `VITE_APP_VERSION`: produced by a `define` in `plugins/metadata.ts:104`; no application code reads it.
- `VITE_MINIO_PUBLIC_URL` and `VITE_SENTRY_DSN`: read in code (`bootstrap/env.ts`, `main.ts`) but absent from all three `.env` files, so they are `undefined` at runtime. Sentry only initializes inside the `import.meta.env.PROD` branch and a missing DSN means nothing is reported; without a MinIO URL, downloads keep going through the proxy prefix (`packages/core/base/shared/src/utils/download.ts`). :::

`vite-plugin-iconify-offline`, `@vitejs/plugin-legacy` and `vite-plugin-cdn-import` are listed in `apps/web/package.json` devDependencies but **never imported**. Offline icons come from `@tomjs/vite-plugin-iconify` (see [Icons](/en/guide/essentials/icons)). Search for an import before assuming a declared plugin is active.

## vite.config.ts and merge order

`apps/web/vite.config.ts` has one meaningful statement:

```ts
// apps/web/vite.config.ts:14-16
export default defineApplicationConfig({
  base: './',
});
```

Options accepted by `defineApplicationConfig(options)` (`internal/vite-config/src/config/application.ts:78-132`):

| Option | Default | Notes |
| --- | --- | --- |
| `base` | `'./'` | pairs with hash history so the output works from any static directory |
| `root` | `process.cwd()` | decides `envDir`, the aliases, and which `package.json` feeds `__APP_INFO__` |
| `port` | — | fallback port, lower priority than `VITE_PORT` |
| `appInfo` | `true` | whether `__APP_INFO__` is injected |
| `define` | — | extra `define` constants |
| `plugins` | — | appended to the shared plugin list (concatenation, not replacement) |
| `overrides` | — | **deep-merged last**, this is where project-specific config belongs |

Merge order is `common → application → overrides` (two `mergeConfig` calls at `:127-130`). Deviate through `overrides` rather than rewriting the config in the app: if `createCommonConfig()`'s aliases and `dedupe` get lost, the symptom is "it runs, but type-check explodes / two Vue runtimes appear at runtime".

`createPlugins()` branches on artifact kind (`internal/vite-config/src/plugins/index.ts:55-213`): only `application` gets HTML injection, PWA, archiving and metadata; `library` keeps the compile chain plus `.d.ts`.

::: warning

`VITE_INJECT_APP_LOADING=false` does not skip the plugin The entry always contains `import { loadingFadeOut } from 'virtual:app-loading'`. Skipping the plugin entirely makes the virtual module unresolvable and the build fails with a 500; the switch therefore only controls injection, and when nothing was injected those functions find no container and do nothing (`plugins/index.ts:157-164`). :::

## User preferences

`packages/core/preferences` exposes a factory plus a module-level singleton whose _creation moment belongs to the app_ (`preferences.ts:148-155`); the project adapter is `apps/web/src/settings/index.ts`:

```ts
// apps/web/src/settings/index.ts:61-64
export const APP_DEFAULTS: AppSetting = withDefaultPreferences({
  copyrightCompany: import.meta.env.VITE_APP_TITLE || 'Antdv Admin',
  watermarkContent: import.meta.env.VITE_APP_TITLE || 'Admin',
});
```

```ts
// apps/web/src/settings/index.ts:92-97
export function getPreferences(): PreferencesInstance {
  return initPreferences({
    defaults: APP_DEFAULTS,
    migrate: migratePreferences,
  });
}
```

Three decisions worth remembering:

- **The instance must be created lazily.** Calling `initPreferences()` at module top level runs before `bootstrap/env` injects the prefix, so reads and writes hit the default `app_cache_*` keys (that default prefix is `packages/core/base/shared/src/utils/env.ts:27`) — the symptom is "my settings save but vanish on reload". The singleton belongs to the package: `initPreferences()` is idempotent (`current ??= createPreferences(options)`, `preferences.ts:160-165`), so `getPreferences()` may be called again from any call site; using it before initialization throws instead of silently building a second config (`getPreferencesInstance()`, `preferences.ts:168-175`).
- **No `import.meta.env` inside defaults** (`packages/core/preferences/src/config.ts:10-14`): the package output sits in `dist`, out of reach of static replacement, so such fields silently become empty strings. Project-specific values enter through `defaults`.
- **The read chain is cache → `migrate` → `pickKnownPreferences` → merged over defaults** (`readMerged()`, `packages/core/preferences/src/preferences.ts:56-60`). `pickKnownPreferences` drops type-mismatched values; `migrate` handles values that are valid strings but obsolete enum members (old layout names). Migration runs on read only.

The full key list, grouped as theme / layout / widgets / footer / general, is `DEFAULT_PREFERENCES` at `packages/core/preferences/src/config.ts:20-80`; persistence uses `PREFERENCES_CACHE_KEY = 'appSetting'` (`constants.ts:11`), prefixed by the cache layer (`shared/src/cache/index.ts:40-45`). How those keys drive the DOM and the antd theme is in [Theming and preferences](/en/guide/in-depth/theme), and how `appStore` flattens them is in [State management](/en/guide/essentials/stores).

## Adding a variable

1. Put it in the right `.env`: shared across modes → `.env`; mode-specific → `.env.development` / `.env.production`.
2. If browser code needs it, let `envParse` regenerate `types/env.d.ts` (any dev or build run does), and judge booleans **only** through `isEnvEnabled`.
3. If only the build needs it (plugins, proxy, HTML injection), read `envConfig` inside `internal/vite-config` and don't also expose it to the browser.
4. Secrets never go into `VITE_*`: anything with that prefix is baked into the bundle and readable in DevTools. To change production settings without rebuilding, enable `VITE_EXTRA_APP` so env lands in a separate `_app-config*.js`.
